# Food catalogue operator CLI

This internal CLI is the controlled entry point for food-source manifests,
independent artifact observations, FDC Foundation inspection, checkpointed and
idempotent database staging, role approvals, promotion, and pointer-only rollback.

It deliberately does not mutate a manifest or manufacture a second acquisition
identity. Checked-in candidates remain templates until two authenticated operators,
a rights reviewer, a pinned parser, immutable object storage, and executable release
expectations are present.

`artifact observe` always performs a fresh allow-listed HTTPS transfer and writes
the attestation with exclusive-create semantics. It refuses to overwrite an
existing observation file; a cache hit never counts as an independent observation.

Authority-changing commands do not accept a principal on the command line. In a
production release, an access-controlled runner must first validate OIDC or
workload identity and then inject `INGEST_AUTHENTICATION_METHOD`,
`INGEST_AUTHENTICATED_PRINCIPAL_ID`, and
`INGEST_AUTHENTICATION_RUN_REFERENCE` together with a short-lived,
least-privilege database credential. A developer who can set arbitrary process
environment variables or write directly to PostgreSQL is outside this trust
boundary; do not run production promotion from an interactive developer shell.
Approval rows and activation reasons retain the authentication method and run
reference; approval time is generated by the database rather than accepted from
the caller.

The release runner must also inject `INGEST_PARSER_BUILD_SHA256`, calculated from
the reviewed immutable parser image/build. Staging refuses a mismatch and binds
the build digest and current nutrient-mapping revision digest into the batch
identity, parser report, and validation evidence.

Run from the repository root after building workspace dependencies:

```sh
pnpm --filter @nutrition-tracker/ingest cli -- manifest validate \
  data/manifests/usda-fdc-foundation-json-2026-04-30.candidate.json
```

See [`infra/runbooks/food-source-release.md`](../../infra/runbooks/food-source-release.md)
for the release procedure. Database promotion requires three distinct immutable
approvals bound to the manifest and validation digests.

`catalogue stage-fdc` requires content-addressed, object-locked artifact and
manifest URIs; the manifest URI must contain the exact manifest SHA-256.
It checkpoints every committed record chunk. Replaying a
partially staged chunk is byte-for-byte idempotent; replaying a validated or
completed batch returns its validation result instead of reopening it. A mapping
revision change invalidates the old attempt and creates a new mapping-digest-bound
batch on replay.

Nutrient mappings are never inferred from staged rows. A reviewer supplies a
mapping file to `catalogue mappings`; the database resolves source nutrient keys
through that reviewed mapping during validation and materialization.
